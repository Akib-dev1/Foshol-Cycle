**Scope:** `src/calendar_evaluator.py`, `tests/test_calendar.py`, `council/reports/E4-builder.md`. E4 covers §6.1 calendar eligibility and §17.1–17.5. §10.4 is in scope only for the waiting policy that §6.1 applies to a future first-crop window. ## Non-blocking observations

1. **Missing `date_precision` after the preferred window is treated as `unsupported`, not `unknown`.** The code requires `date_precision` only inside the preferred branch (`src/calendar_evaluator.py:186-193`); the late and outside branches (`:212-239`) do not re-check it. A profile with a blank `date_precision` and a date after the preferred window therefore returns a definitive `unsupported` / `OUTSIDE_SUPPORTED_WINDOW` (probe: 2026-08-01). The spec's item 4 says "Missing or geographically inappropriate window evidence: unknown" (`v1.md:157`), and §5 says unknown values "do not automatically prove that a crop cannot grow" (`v1.md:144`). This is non-blocking for the current eight profiles because all carry a concrete `date_precision`; the result is conservative (not a pass), not favorable. Hardening: require usable precision for any late/outside result, or return `unknown` when it is absent, and add an outside/late missing-precision test alongside `tests/test_calendar.py:256-272`.

2. **A late-end-only cross-year window is attached to the preferred end year.** `_build_candidate` attaches `late_end` to `end_year`, which is `start_year + 1` only when `window_crosses_year` is true (`src/calendar_evaluator.py:249-252`). A profile with a non-crossing preferred window (for example `12-01..12-15`) and a late end in January would attach the late end to December's year and silently lose the late support; `_support_end` would also ignore it (`:310-315`). The Boro case is correct because the preferred window itself crosses. No current profile has this shape. Hardening: validate that the late end is after the preferred end after year attachment, or add an explicit late-window cross-year field and return `unknown` for an inconsistent shape.

3. **Geographic mismatch detection is a token match, not a structured scope check.** The evaluator flags `NOT_RAJSHI_EXACT` (the data's spelling) or `LOCATION_TRANSFERABILITY` in the free-text metadata (`src/calendar_evaluator.py:118-121`). The current mung profile is caught (`tests/test_calendar.py:193-199`), but a future profile with the correctly spelled `NOT_RAJSHAHI_EXACT`, or a different phrase such as `INDIA_OPTIMUM`, would pass a preferred window. Hardening: add a structured geographic-scope field to the profile and branch on that, keeping the token check as a fallback.

4. **The within-limit reason does not state the limit's basis; the API cannot express a sourced agronomic basis.** The exceeds reason correctly says "The limit is a product relevance cutoff" (`src/calendar_evaluator.py:175-181`), but the within-limit reason only says "within the configured maximum waiting limit" (`:166-174`). `details` expose `waiting_limit_days` and `waiting_limit_status` but no `waiting_limit_basis` (`:333-353`), and `max_waiting_days` accepts only a number (`:23-38,401-408`). §10.4 says "Every limit must state its basis" (`v1.md:311-314`). This is non-blocking because the only implemented policy is a product-relevance cutoff and the exclusion path states it; the within-limit path does not call it a scientific maximum. Hardening: add a `waiting_limit_basis` value (`product_relevance` or a caller-supplied sourced constraint) and include it in both reasons and details.

5. **After a window has ended, the evaluator prefers outside support over the next season's future option.** `_select_candidate` chooses the nearest start among the considered candidates (`src/calendar_evaluator.py:281-307`). For a date well after the current window but before the next one, this yields `unsupported` for the current opportunity instead of a `FUTURE_WINDOW_*` result (for example Boro 2026-06-01). This is the builder's deliberate §17.3 choice (`council/reports/E4-builder.md:87-90`) and avoids silently advancing a season; it is not a spec violation, but it means a future option within a configured maximum wait can be hidden when the just-expired season is nearer. Product intent should confirm this is desired.

6. **Overall candidate/conditional/not-supported aggregation and range-level partial exclusion are downstream.** E4 emits the check status and `waiting_limit_status`; E9 owns the overall status (`council/CHECKLIST.md:71`) and E6 owns the range-level partial-vs-complete exclusion (`council/CHECKLIST.md:68`). E4 does not itself present a crop as a candidate, so §17.3's "not presented as a normal candidate" is proven at the check level here and must be preserved by the E9 aggregator.

## Verdict

**PASS** — E4 implements the §6.1 preferred, late, outside, and unknown outcomes; the required "outside the documented window" wording and the prohibition on calling the preferred end a proven biological deadline; the future-window plant-after-waiting behavior with an exposed earliest date and a configurable, default-free maximum wait; correct Boro year attachment and leap-day handling; the lowercase §5/§14.4 status vocabulary; §17.1–17.5; and one profile-driven evaluator with no crop-specific branches. The notes above are non-blocking hardening and wording items: the current eight profiles do not trigger the missing-precision or late-only-cross-year cases, the limit is stated as a product-relevance cutoff on the exclusion path, and overall status/range aggregation belongs to E9/E6. No source or test file was modified by this audit.
