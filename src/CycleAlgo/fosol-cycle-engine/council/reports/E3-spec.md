## Blocking findings

1. **E3-S1 — SMAP/AppEEARS lacks bounded retries and rate-limit handling.** §15 requires "bounded retries, and provider rate-limit handling" (`v1.md:649`). The POWER path implements both (`src/power_api.py:196-215`), but the AppEEARS path raises on the first HTTP error: `src/smap_api.py:200-222` catches every `HTTPError` and immediately raises `AppEEarsResponseError` (or `AppEEarsAuthError` for 401/403); `_request_json`/`_request_bytes` make one call (`:225-272`), and submission/polling/bundle/download have no retry loop (`:275-332, 335-400, 403-488`). A transient AppEEARS 429, 5xx, or network failure therefore aborts the SMAP load (or forces the stale-cache path) instead of retrying. No SMAP retry/429 test exists; the retry tests at `tests/test_environment.py:195-260` are POWER-only. The docs likewise document retry only under POWER failures (`docs/ENVIRONMENTAL_DATA.md:31-39`), not under SMAP (`:85-91`). This is a must-level §15 gap.

2. **E3-S2 — the §2 per-product record is incomplete.** §2 says "Before implementation, record for each selected product" the listed items (`v1.md:75-83`). `docs/ENVIRONMENTAL_DATA.md` records product/version, endpoint/access, auth, units, fill value, and spatial/temporal resolution, but does not record:
   - provider usage limits (`:72-83` covers token expiry only);
   - variable valid ranges (`:20-29` gives units, not ranges);
   - temporal coverage (`:148-155` only says coverage differs);
   - publication latency (`:148-155` only says latencies differ);
   - the representative location coordinates and the exact method used to associate observations with the selected district (`:113-114` covers observation-vs-retrieval time only; `:150-155` says point, not district average).

   The request object carries `point_id` and coordinates (`src/environment.py:377-390`), but that is not a documented association method. This is a must-level §2 record gap and also leaves §19's "unresolved items must remain visible" only partially satisfied.

## Non-blocking observations

1. **No request-to-response cross-check for coordinates or requested period.** POWER drops the response `geometry` (`src/power_api.py:339-352`) and validates only header start/end consistency (`:320-333`); SMAP validates the CSV contains one point (`src/smap_api.py:583-590`) but never compares that point or the returned timestamps to the requested latitude/longitude/date range. A provider response for a different point or a short period would still be cached under the requested key and reported with the requested `request` metadata. Structural validation is present, so this is a hardening gap rather than the §15 "validate provider responses" failure.
2. **The POWER cache key uses the hardcoded `POWER_PRODUCT_VERSION`, not the normalized response version.** `POWER_PRODUCT_VERSION = "v2.10.3"` (`src/power_api.py:21`) is passed to `build_cache_key` at `src/environment.py:183`, while the record's `product_version` is read from `header.api.version` (`src/power_api.py:267-271, 341`). If NASA changes the API version, the key will not change until this constant is edited; the normalizer also does not compare the two.
3. **A single 7-day TTL is used for both providers.** `src/environment.py:36-38` defines separate constants but gives both `7 * 24 * 60 * 60`; the docs calls this an explorer policy, not a publication-latency claim (`docs/ENVIRONMENTAL_DATA.md:130-132`). For a request whose `end_date` is recent, a cached response up to seven days old can be returned as fresh even if newer observations have since been published. The spec's "appropriate to each product's publication schedule" (`v1.md:647`) is only weakly satisfied.
4. **Caching is exact-range, not day-level.** `build_cache_key` includes `start_date` and `end_date` (`src/environment_cache.py:30-39`), so two branches requesting overlapping but non-identical history share no days. The same request is shared (`tests/test_environment.py:689-749`), which satisfies the literal "same cached history" for identical requests, but not overlapping windows.
5. **No QA layer is requested.** The docs says "No separate QA layer was returned for these two layers; none is invented" (`docs/ENVIRONMENTAL_DATA.md:70`), and the real fixture confirms the two columns (`tests/fixtures/appeears_spl4smgp_rajshahi_20250101_20250103.csv:1`). This is acceptable for the selected layers, but the claim should be verified against the product's full layer list if a QA flag exists; the code would ignore any extra QA column.
6. **The §19 historical period and coverage requirement remain unrecorded.** E3 correctly does not implement seasonal replay, but the docs do not state the historical period/coverage rule that E7 must apply. This is not an E3 data-layer defect, but it remains an open evidence item and is not surfaced in any result yet.

## Round 1 verdict (superseded by Round 2)

**FAIL** — the E3 data layer correctly handles cache keys, shared requests, observation/retrieval timestamps, `-999`/`-9999` missing sentinels, stale-cache warnings, partial provider failure, zero-vs-missing preservation, point-vs-district disclosure, and the SMAP product/access decision. However, two must-level requirements are not met:

1. §15 (`v1.md:649`) requires bounded retries and provider rate-limit handling; the AppEEARS/SMAP path has neither (`src/smap_api.py:200-222`).
2. §2 (`v1.md:75-83`) requires a per-product record of usage limits, valid ranges, coverage, publication latency, and the district-association method; `docs/ENVIRONMENTAL_DATA.md` omits all five.

These are compliance blockers, not code-style preferences. No source or test file was changed by this audit.
